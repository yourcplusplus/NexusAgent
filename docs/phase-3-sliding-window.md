# Phase 3:滑动窗口压缩

## 核心问题

旧压缩在 token 超限时做一件事:`RemoveMessage(REMOVE_ALL_MESSAGES)` 把转录整表清空,只留一条 LLM 摘要。三个后果叠在一起:关键信息(路径、产物指针、进行中的 todo)全押在那一次摘要上;摘要覆盖式重写,每轮都在摘要的摘要上再摘要,衰减不可逆;压缩本身还要把全部消息喂给模型,转录越大,这一步自己越可能先爆。

## 机制

第一步是让「逐出」有单位。给每个节点产出的消息盖确定性 ID(`<node>-a<attempt>-<seq>`),压缩时按前缀把连续段切成组——一次节点执行就是一组,不额外引入 state 字段。转录的首条 HumanMessage 钉住,永不逐出。

逐出多少由两个约束取更严者:组数上限,和 token 上限(限额的 30%)。有一条刻意的设计:最新一组永远保留,哪怕它单独超出 token 上限——组内配对必须完整、没法切分,而 Phase 1 的落盘已经让单组天然有界。

逐出还有一条不能破的不变量:工具调用和它的结果必须在同侧,否则下次发给模型就是 400。两条规则兜底:结果被拆散了就拉回来(宁可少逐出),孤儿结果就踢出去,一轮收敛。

被逐出的内容不直接扔,只把这些片段喂给模型做增量 rollup——不喂全量转录,压缩这一步自己就不会爆。模型不可用时走确定性 fallback,逐条提取,产物指针和退出码保得住。叙事的超限处理也换了思路:最旧条目压成单行,新条目永远完整,「摘要的摘要」式的衰减从机制上消掉了。

监控顺手也重写了。旧实现每次全量 tokenize、还要读盘;现在按组求和、复用已有的记忆快照估载荷,零磁盘 I/O、零模型调用。压力过七成发一次预警事件,回落后自动重新武装。

## 涉及文件

新增 `graph/context_window.py`——纯函数,不读 state、不调模型、不碰盘,分组/窗口/闭合全在这里,单测不用起图。`nodes.py` 做 ID 盖章、增量估算、软阈值、压缩器重写,顺手删了 6 个旧/死函数;`memory.py` 加 rollup、fallback、折叠;`state.py` 加一个标志位;`prompts/stage4.py` 换提示词。

## 测试

212 个测试通过。新增 24 个:分组、双约束窗口、两条闭合规则、无 ID 消息的防御、三条跳过路径、折叠、fallback 指针、端到端的白名单隔离。另有 4 处既有测试更新——逐条删除断言重写、估算打桩拆分、压缩器重写、白名单断言改成「压缩路径不搬运白名单」。

## 自查修复的真缺陷

折叠桶(最多留 12 条快照)在小上限下会把空间吃满,把尾部最新的条目截掉——而最新条目恰恰是唯一必须完整的。改成桶只用剩余预算,不与正文抢空间。

## 漏算的测试

有一个测试漏算了:`test_estimate_context_tokens_uses_model_counter` 断言的是旧 tokenizer 行为,这一步改完必挂。根因是 grep 影响面时只查了「谁调用它」,没查「谁直接测它」——影响面 grep 必须把被测符号名本身也盖住。
